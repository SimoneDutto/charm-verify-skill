# charm-verify

An agent skill that builds a TLA+ model of your Juju charm, checks it with TLC,
and explains failures against the source code.

Requires an agent that supports skills and MCP tools, a local charm repository,
and a TLA+ MCP server. No existing model needed.

## Example

An example run on the PostgreSQL charm, shortened to 30 seconds.

![Example run on the PostgreSQL charm](verification.gif)

It is possible to expand on each finding, asking questions, create a Python test reproducer, and so on.

## How is this different from asking an LLM to "find bugs"?

Since this is a skill, not a different model, it is hard to measure how much it
improves on a plain prompt. In my view, the main benefits are:

- grounding: the AI writes an explicit model and properties, and TLC checks them. You get an event ordering to inspect, not just an explanation of why something might be a bug.
- iterating on it: you can explore a new scenario while rechecking the existing properties, without reminding the AI of every earlier concern. Those concerns live in the specification rather than only in the chat. TLC explores the allowed event orderings within the model's bounds, including combinations you might not think to ask about individually.
- learning TLA+: a charm already behaves much like a state machine, so TLA+ is a useful fit. The generated model can also be a way to learn TLA+: read it, question its assumptions, and gradually replace it with a specification you understand and maintain
yourself. That is useful even beyond the first round of bug finding.
- (unsure) credits spending: the first TLA+ specification generation is more expensive, but testing new invariants and constraints is not, so you can keep testing new features at relatively low cost.

## Instructions

### First run

Clone this repository into your client's skills directory. For example, for
Copilot:

```sh
git clone https://github.com/SimoneDutto/charm-verify-skill.git ~/.copilot/skills/charm-verify
```

Open your charm repository in your agent's workspace. Configure and enable a
TLA+ MCP server that exposes SANY parsing and exhaustive TLC checking.

Load the `charm-verify` skill using your client's skill command or ask the agent
to use it. Installation paths and invocation syntax vary by client. Then ask:

```text
Verify the charm in this workspace using the skill `charm-verify`
```

The skill reads event handlers and their dependencies, records the mechanisms
and interactions it covers, and builds a model. It parses that model, runs a
baseline check, then checks each invariant and temporal property independently.
A failed property does not stop the remaining checks.

The response includes each check's status, an explanation of any counterexamples,
and links to the saved evidence. A timeout or unfinished check is not a pass.
A passing bounded model is not proof that the Python charm is correct.

### Generated files

By default, files go under the charm's `tla/` directory, not this skill's directory.
An investigation looks like this; scope names and trace filenames vary:

```text
tla/
  CharmModel.tla                 # editable model
  CharmModel.cfg                 # editable configuration and property set
  verification/
```

Imported local TLA+ modules are snapshotted too. Each check has isolated inputs.
Later runs create new attempt directories; they do not overwrite old evidence.
Start with the report to understand a result, and use the logs and traces to
inspect exactly what the checker returned.

#### What to commit

Commit the working `.tla` and `.cfg` files, including any local TLA+ modules the
model imports. The `verification/` directory is generated analysis output, not
something you need to keep in Git. Add this to your charm repository's `.gitignore`:

```gitignore
/tla/verification/
```

Keep it locally while investigating or iterating, then delete it when you are
done. Deleting it removes the reports, traces, and saved context for continuing
that analysis; you can still run new checks from the committed model.

It is useful to track the `.tla` and `.cfg` files, because it makes next iterations and new explorations quicker and cheaper.

### What the output like

*Verification complete*: _summary_

*Bounds*: _checks done_

*Findings*: _findings_

Deliverables: _files generated by the skills_

You can then ask to expand, explain each finding with contextual knowledge about the charm and TLA counterexample. You can even ask the LLM to verify specific scenario you think the TLA state machine modelling would be a good fit for.
